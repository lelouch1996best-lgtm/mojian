# 墨间桌面客户端 · 构建与序列号签发指南

> 本文档面向开发者，说明如何把墨间打包为可安装的桌面客户端，以及如何为用户签发序列号。

---

## 一、整体方案概览

| 能力 | 实现 |
|------|------|
| 客户端外壳 | Electron 内嵌 Next.js standalone 服务（保留服务端 API / better-sqlite3 / COS SDK） |
| 序列号验证 | Ed25519 离线签名，App 内嵌公钥本地验签，无需 license 服务器 |
| 版本作用域 | 序列号绑定主版本号，`1.x` 共用一码，跨主版本（`2.x`）需换号 |
| 有效期 | 开发者签发时决定：永久或限时（按天） |
| 机器绑定 | 可选绑定具体机器指纹（防分享），或通配符 `*` 一码通用 |
| 加密存储 | 激活记录经 Electron safeStorage（系统级加密）保存 |

**核心安全前提**：私钥（`electron/keys/private.pem`）只由开发者持有、绝不入库。私钥一旦泄露，已签发序列号无法回收，需重新生成密钥对并重新发布应用。

---

## 二、环境要求

- Node.js 18+（推荐 20）
- npm 10+
- 首次安装 Electron 依赖较慢，国内网络建议使用镜像（见下）

> **无需 Python / C++ 工具链**：better-sqlite3 的原生模块通过 `prebuild-install` 直接下载官方预编译二进制（覆盖 Electron ABI），electron-builder 打包时也会自动处理。仅在极少数情况（better-sqlite3 未发布对应 Electron 版本的预编译包）才需从源码编译，此时手动执行 `npm run electron:rebuild`，并准备：
> - macOS：Xcode Command Line Tools（`xcode-select --install`）
> - Windows：Visual Studio Build Tools（含 C++ 工作负载）+ Python 3.x
> - Linux：`build-essential` / `python3`

## 三、首次准备

### 1. 安装依赖

```bash
npm install
```

> 国内网络若 Electron 下载缓慢或失败，使用镜像：
> ```bash
> export ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/
> export ELECTRON_BUILDER_BINARIES_MIRROR=https://npmmirror.com/mirrors/electron-builder-binaries/
> npm install --registry=https://registry.npmmirror.com
> ```
>
> 上述两个镜像变量在**打包阶段同样必需**：electron-builder 运行时会从 GitHub 下载 Electron 二进制和 NSIS/winCodeSign 等打包工具，国内直连 GitHub 基本会超时。建议写入 shell 配置（`~/.zshrc` / 环境变量）永久生效，避免每次手动 export。

### 2. 生成 Ed25519 密钥对

```bash
npm run gen:keypair
```

该命令会在 `electron/keys/` 下生成：
- `public.pem` —— 公钥，**随应用打包分发**，App 启动时用于验签
- `private.pem` —— 私钥，**严禁入库**，仅在签发序列号时使用

> `.gitignore` 已包含 `*.pem`，两个密钥文件默认都不会被提交。
> 公钥需要随应用分发，提交时请显式执行：
> ```bash
> git add -f electron/keys/public.pem
> ```
> 私钥请额外备份到安全位置（如密码管理器），丢失后无法再签发同密钥的新序列号。

## 四、开发模式运行

开发模式下 Electron 窗口会加载 `next dev` 起的开发服务器，支持热更新：

```bash
npm run electron:dev
```

该脚本会并发执行：启动 `next dev` → 等待 3000 端口就绪 → 编译 Electron 主进程 → 启动窗口。

- 未激活时窗口自动加载 `/activate` 激活页
- 开发模式下 `lib/auth.ts` 自动放行鉴权，无需配置 token
- 数据库写入 `app.getPath('userData')/data/mojian.db`

## 五、构建可安装客户端

### 完整打包命令

```bash
npm run electron:build
```

该命令按顺序执行：

| 步骤 | 说明 |
|------|------|
| `electron:build:next` ∥ `electron:compile` | **并行**：前者 `next build`（standalone 模式）并内联本地鉴权 token；后者编译 `electron/*.ts` → `dist-electron/*.js`。两者无文件依赖，并行执行节省时间 |
| `electron:rebuild:standalone` | 把 standalone 产物里的 better-sqlite3.node 替换为 **Electron ABI** 版本（详见下文「原生模块 ABI 说明」） |
| `electron-builder` | 按 `electron-builder.yml` 打包安装包 |
| `electron:restore:native` | 恢复 better-sqlite3 的 **Node ABI**，保证打包后 `npm run dev` 仍可用（详见下文「原生模块 ABI 说明」） |

### 原生模块 ABI 说明

better-sqlite3 是 C++ 原生模块，编译产物 `better_sqlite3.node` 必须匹配宿主运行时的 ABI：

| 场景 | 运行时 | ABI | .node 位置 |
|------|--------|-----|-----------|
| `npm run dev`（Next 开发服务器） | Node.js | Node ABI | `node_modules/better-sqlite3/build/Release/` |
| 打包后的墨间应用 | Electron | Electron ABI | 安装包内 `resources/app/node_modules/...`（独立副本） |

#### 为什么需要 `electron:rebuild:standalone`

Next.js standalone 模式会从 `node_modules` 复制 better-sqlite3（含 .node）到 `.next/standalone/node_modules/`。但此时 .node 是 **Node ABI** 版本（`npm install` 时下载的），Electron 运行时加载它会报 `NODE_MODULE_VERSION` 不匹配，导致所有数据库 API 返回 500。

electron-builder 的 `install-app-deps` 只处理项目根目录的 `node_modules`，**不会修复 standalone 产物里的原生模块 ABI**。因此需要在 `next build` 之后、`electron-builder` 之前，用 `electron:rebuild:standalone` 脚本（`tools/rebuild-standalone-native.ts`）通过 `prebuild-install --runtime electron` 下载 Electron ABI 的预编译二进制，覆盖 standalone 里的 .node。

#### 打包后的 ABI 流转

```
npm install → 下载 Node ABI 的 .node (ABI 137)
    ↓
next build → standalone 复制 Node ABI 的 .node
    ↓
electron:rebuild:standalone → 替换为 Electron ABI 的 .node (ABI 125)
    ↓
electron-builder → 把 standalone 复制到 resources/app/（含 Electron ABI 的 .node）
    ↓
electron:restore:native → 把 node_modules 里的 .node 恢复为 Node ABI
```

**两个版本不并存于 node_modules**，是同一个文件被来回替换。打包后的 `resources/app/` 里有独立的 Electron ABI 副本，不受后续 `npm install`/`npm rebuild` 影响。

> **为何 restore 步骤需要单独脚本**：electron-builder 运行时会在进程环境中注入 `npm_config_runtime=electron`、`npm_config_node_gyp=@electron/node-gyp`、`npm_config_disturl=https://electronjs.org/headers` 等变量，这些变量会持续到后续的 `npm rebuild`，导致 restore 步骤误以为要构建 Electron ABI（进而触发 node-gyp 源码编译，需要 Python）。`electron:restore:native` 脚本先清除这些环境变量再执行 `npm rebuild better-sqlite3`，确保恢复为 Node ABI。

### 打包前注意事项

- **关闭 dev 服务器**：打包前确保 `npm run dev` / `npm run electron:dev` 已停止。开发服务器会加载 `better_sqlite3.node`，导致 electron-builder 替换该文件时在 Windows 上报 `EBUSY: resource busy or locked`。
- **国内网络**：electron-builder 运行时需从 GitHub 下载 Electron 二进制和 NSIS/winCodeSign 等工具。国内需设置镜像环境变量（见第三章），否则下载超时。

### 产物

安装包输出到 `dist-installer/` 目录：

| 平台 | 产物格式 |
|------|---------|
| macOS | `.dmg` + `.zip` |
| Windows | `.exe`（NSIS 安装器） |
| Linux | `.AppImage` |

### 单独执行某一步（可选）

```bash
npm run electron:build:next        # 仅构建 Next standalone 产物
npm run electron:compile           # 仅编译 Electron 主进程
npm run electron:rebuild:standalone # 仅替换 standalone 里的 better-sqlite3.node 为 Electron ABI
npm run electron:rebuild           # 手动从源码重编译 better-sqlite3 为 Electron ABI（仅 prebuilt 不存在时才需要，需 Python）
```

### 打包注意事项

- **跨平台打包**：electron-builder 默认只能打包当前操作系统。如需在 macOS 上打 Windows 包等跨平台场景，请参考 electron-builder 多平台构建文档，通常需要 Docker 或 CI。
- **应用图标**：当前未配置自定义图标，使用 Electron 默认图标。如需自定义，在 `electron-builder.yml` 的 `mac.icon` / `win.icon` / `linux.icon` 指向 `build/` 下的图标文件（macOS 需 `.icns`，Windows 需 `.ico`）。

### macOS 签名与公证（解决「文件已损坏」）

macOS 从 Catalina 起强制要求分发应用经签名 + 公证。未签名的 dmg 发给用户会提示「文件已损坏」或「无法验证开发者」，这是 Gatekeeper 拦截，**不是芯片差异**。

**正式分发需 Apple 开发者账号（$99/年）：**

1. 在 [Apple Developer](https://developer.apple.com) 申请 `Developer ID Application` 证书，导入到「钥匙串访问」
2. 记下 Team ID（开发者后台 Membership 页可见）
3. 申请 App-Specific Password（用于公证，[appleid.apple.com](https://appleid.apple.com) 生成）
4. 打包前设置环境变量：

```bash
export CSC_LINK="Developer ID Application: Your Name (TEAMID)"   # 证书名（钥匙串中显示的完整名）
export CSC_KEY_PASSWORD="your-keychain-password"                  # 钥匙串访问密码（通常可留空，会弹窗）
export APPLE_ID="your-apple-id@email.com"                         # 公证用 Apple ID
export APPLE_APP_SPECIFIC_PASSWORD="xxxx-xxxx-xxxx-xxxx"          # App 专用密码
export APPLE_TEAM_ID="TEAMID"                                     # Team ID
export NOTARIZE_TEAM_ID="TEAMID"                                  # electron-builder notarize 配置读取
```

5. 执行 `npm run electron:build`，electron-builder 会自动：签名 -> 公证 -> 装订公证票据

> 配置已在 `electron-builder.yml` 的 `mac` 段就绪（`hardenedRuntime` / `entitlements` / `notarize`），entitlements 文件在 `build/entitlements.mac.plist`。未设置上述环境变量时，electron-builder 会回退为 ad-hoc 签名（仅本机可用）。

**临时方案（无开发者账号、小范围测试）**：让用户在终端执行以下命令解除隔离属性后即可运行，但不适合正式分发：

```bash
xattr -cr /Applications/墨间.app
```

## 六、签发序列号

提供两种签发方式：**网页工具（推荐）** 和命令行。

### 方式一：网页工具（推荐）

启动本地签发工具：

```bash
npm run license:tool
```

终端会提示打开浏览器访问 `http://127.0.0.1:7788`。在网页表单中填写：

| 字段 | 说明 |
|------|------|
| 机器码 | 用户从激活页复制的机器码直接粘贴（带 `-` 分组或原始 hex 均可）；填 `*` 表示一码通用 |
| 主版本号 | 须与 App 主版本一致（默认读取 package.json） |
| 有效期（天） | `0` = 永久；`365` 表示 365 天 |
| 授权等级 | 预留字段，默认 `pro` |

点「生成序列号」后，页面会显示可读分组的序列号、一键复制按钮，以及 payload 摘要（产品/机器码/主版本/签发时间/有效期/等级）。

> 该工具仅在 `127.0.0.1` 本地运行，私钥不会离开本机。**绝不可对外公开此端口或部署到服务器**（涉及私钥安全）。工具代码位于 `tools/license-tool.ts`，已被 electron-builder 的 files 白名单排除，不会打包进客户端。

### 方式二：命令行

```bash
npm run gen:license -- --machine <机器码> --vmaj <主版本号> [--days <天数>] [--tier <等级>] [--private <私钥路径>]
```

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `--machine` | `*` | 机器码。`*` 表示通配（一码通用）；否则填用户提供的机器码（分组形式带 `-` 也可，会自动归一化） |
| `--vmaj` | package.json 主版本号 | 序列号适用的主版本号，须与目标 App 主版本一致 |
| `--days` | `0`（永久） | 有效期天数。`0` 或不传为永久；`365` 表示 365 天 |
| `--tier` | `pro` | 授权等级（预留字段） |
| `--private` | `electron/keys/private.pem` | 私钥文件路径 |

### 常用签发场景

以下场景网页工具与命令行均可实现，命令行示例：

```bash
# 1. 永久 + 一码通用（所有用户共用，最省事，但泄露后无法回收）
npm run gen:license -- --machine "*" --vmaj 1

# 2. 永久 + 绑定具体机器（防分享，需逐个签发）
npm run gen:license -- --machine "953c-2df2-5f3b-..." --vmaj 1

# 3. 限时 365 天 + 绑定机器
npm run gen:license -- --machine "953c-2df2-5f3b-..." --vmaj 1 --days 365

# 4. 限时 30 天试用 + 通配
npm run gen:license -- --machine "*" --vmaj 1 --days 30
```

执行后会在终端输出格式化的序列号（每 5 字符一组用 `-` 分隔，便于阅读），以及 payload 摘要。把序列号字符串发给用户即可。

### 版本升级时的处理

- **小版本/补丁升级**（如 `1.2.0` → `1.2.3`）：主版本号仍为 1，用户**无需重新激活**。
- **跨主版本升级**（如 `1.x` → `2.0.0`）：主版本号变为 2，旧序列号失效，用户需重新激活。你需用 `--vmaj 2` 签发新序列号：

```bash
# 发布 2.0.0 前，先把 package.json version 改为 2.0.0，再用新主版本签发
npm run gen:license -- --machine "953c-2df2-..." --vmaj 2
```

## 七、用户激活流程

终端用户的操作非常简单，激活页已内置全部引导：

1. 用户安装并打开客户端
2. 因未激活，自动进入 `/activate` 激活页
3. 页面显示**本机机器码**，用户点「复制」按钮复制到剪贴板
4. 用户把机器码通过微信/QQ/邮件等渠道发给你
5. 你用 `gen:license` 签发序列号，把序列号发回给用户
6. 用户把序列号粘贴到激活页输入框，点「激活」
7. 验签通过 → 自动进入主应用

> 激活记录经系统级加密（macOS Keychain / Windows DPAPI / Linux libsecret）保存到用户数据目录。后续启动会自动校验记录，无需重复输入。若换机、过期或跨主版本升级，记录失效后自动清除并回到激活页。

## 八、机器码收集渠道建议

| 渠道 | 适合场景 | 说明 |
|------|---------|------|
| 微信/QQ 私聊 | 用户量小 | 最简单，手动粘贴机器码、手动发序列号 |
| 邮件 | 有官网/留了邮箱 | 留痕，但往返慢 |
| 在线表单（飞书/腾讯文档/金数据） | 用户稍多 | 用户填机器码+联系方式，集中处理 |
| 网页表单 + 自动签发后端 | 用户量大 | 用户粘贴机器码，后端自动调 `gen:license` 签发回传，无人值守 |

> 机器码本身不是敏感信息（是硬件标识的哈希），可以明文传输。真正需要保密的是你的私钥。

## 九、安全与运维要点

### 私钥管理
- `electron/keys/private.pem` 是整个授权体系的根，**绝不入库、绝不分发**
- 务必备份到安全位置（密码管理器、加密U盘等）
- 若私钥泄露：重新 `npm run gen:keypair` 生成新密钥对 → 用新公钥重新打包发布应用 → 旧序列号全部失效，所有用户需重新激活

### 通配 vs 绑定的权衡
- **通配符 `*`**：一码通用，签发即分发，运营成本低。风险是序列号一旦泄露可被任意传播，你无法回收。
- **机器绑定**：逐个签发，运营成本高，但序列号绑定具体机器，换机即失效，无法被分享。
- 早期铺量可用通配降低摩擦，用户量起来后切到机器绑定。两种模式代码均已支持，按需选用。

### 吊销与续期
- 离线模型**无法远程吊销**已签发的永久序列号。若需吊销能力，只能：换公钥重新发布应用，使旧序列号全部失效。
- 限时序列号到期后自动失效，用户需重新签发续期，天然具备「到期回收」能力。如需可控的续期节奏，优先用限时序列号。

## 十一、目录结构说明

```
mojian/
├── electron/                    # Electron 主进程相关
│   ├── main.ts                  #   主进程：启动服务、激活门禁、IPC
│   ├── preload.ts               #   预加载：向渲染进程注入 window.electronAPI
│   ├── license.ts               #   序列号验签核心逻辑
│   ├── machine-id.ts            #   跨平台机器指纹
│   ├── activation-store.ts      #   safeStorage 加密存储激活记录
│   ├── types.ts                 #   IPC 类型定义
│   ├── tsconfig.json            #   主进程独立 TS 配置（CJS 输出）
│   └── keys/                    #   Ed25519 密钥（私钥不入库）
│       ├── public.pem           #     公钥（git add -f 提交）
│       ├── private.pem          #     私钥（.gitignore 已排除）
│       └── README.md
├── tools/                       # 开发者侧工具
│   ├── gen-keypair.ts           #   生成密钥对
│   ├── gen-license.ts           #   命令行签发序列号
│   └── license-tool.ts          #   网页签发工具（本地 127.0.0.1）
├── app/activate/page.tsx        # 激活页 UI
├── electron-builder.yml         # 打包配置
├── electron-globals.d.ts        # 渲染进程 window.electronAPI 类型声明
├── next.config.mjs              # Next 配置（output: standalone）
└── package.json                 # 脚本与依赖
```
